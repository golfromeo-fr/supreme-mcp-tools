Two ISOLATED podman environments, managed by the (local) `startcluster`
script:

| Environment | Purpose | Ports | Data |
|---|---|---|---|
| `work`   | pod-based DAILY DRIVER (alternative to host startlauncher) | canonical 8000-8005, central 8200, UI 8400 (profile) | own pgvector state plane + YOUR real data planes (host .env, host turso dir, host users.json imported once) |
| `test`   | M4 multi-host test bench (two light nodes) | 18200 / 19200 (+18xxx/19xxx tools) | own volumes (pgdata / sqldata) |

Isolation rules:
- separate compose projects (`mcp-work` / `mcp-multihost`) and volumes;
- the work cluster and the host `startlauncher` are mutually exclusive
  (same canonical ports) — the script refuses to start one while the other
  holds the ports;
- automated tests target the canonical ports: stop the work cluster before
  running the suite, or the suite tests the work environment (it is
  self-cleaning).

nodes, optional management UI. This is the H4 practical step: it gives you a
real second node so the shared-state code paths (`MCP_USERS_BACKEND=db`,
`MCP_STATE_BACKEND=db`) run against a real network backend instead of a
local file.

## Phase B/C additions (2026-09-14)

- **LB** (`compose-lb.yml`): nginx round-robin over the node centrals,
  published on **127.0.0.1:18080** (loopback only — it fronts the central
  management API). `X-Upstream` response header shows which node answered.
  The upstream uses `ip_hash`, so stateful `/mcp` clients stay pinned to
  one node; stateless clients are unaffected.
- **MinIO shared artifacts** (`compose-artifacts.yml`): the test cluster's
  nodes become stateless — set `S3_ENDPOINT=http://minio:9000`,
  `S3_ACCESS_KEY=mcp-artifacts`, `S3_SECRET_KEY=<MINIO_ROOT_PASSWORD from
  deploy/.env>` in node.env (bucket `memory-artifacts` is auto-created on
  cluster start; generate a real password into `deploy/.env`, don't ship
  the placeholder).
  MinIO console is internal (:9001); the S3 API is additionally published
  on host **127.0.0.1:19000** for cross-environment verification.
- **Verified live**: LB balancing (X-Upstream alternates), and a 19KB
  memory upserted via node1 read back via node2 with its content served
  from MinIO.
- **Known limitation** (see post-M4 roadmap): the embedded-sqld (turso)
  topology expires idle libsql HTTP streams (`STREAM_EXPIRED`) — pg
  topology recommended for anything beyond boot demos.

## Config bundles (`--config-bundle`)

A **bundle** is a snapshot of every config surface the pods consume, harvested
from the working tree into a plain folder you can edit. A bare NAME goes to
`<cwd>/my-bundles/<NAME>`; a path is honored as-is; no argument defaults to
`<cwd>/my-bundles/bundle-<UTC ts>`:

```bash
./startcluster harvest                    # -> ./my-bundles/bundle-<UTC ts>/
./startcluster harvest toto               # -> ./my-bundles/toto/
./startcluster harvest ~/my-bundles/a     # explicit path — as given
./startcluster harvest --list             # dry-run: show what would be collected
./startcluster harvest --from-work-db     # pull users+masks from the LIVE work DB (fresher than the json seeds)
./startcluster harvest --zip --redact     # shareable copy (secrets blanked; zips are transport-only)
```

Collected: `.env` → `env/.env` · `users.json` + `tools_config.json` →
`identity/` · `config/*.json` · `tools/*/config.json`. Data planes (turso
dir, HF cache) are NOT copied — `manifest.json` records their host paths
plus git sha + per-file sha256.

Seed an environment from a bundle (`-b` is the short form of `--config-bundle`):

```bash
./startcluster work -b ~/supreme-mcp-tools-bundles/config-bundle-20260917-1010
./startcluster test pg -b <bundle-path>                   # same for the test bench
```

- **work**: `work.env` is regenerated from the bundle on every `up` (the
  running DB's password is preserved; the previous env is backed up next to
  it). The bundle's `identity/users.json` is what the one-time import mounts.
- **test**: `node.env` is GENERATED per topology — identity plane verbatim,
  state plane rewritten (`POSTGRES_HOST=db` etc.), and **`file:` data-plane
  lines are stripped** so the bench can never reach your real memory store
  (`--keep-dataplanes` overrides). `users.json` mounts into node1 only: its
  one-time import seeds the shared DB, node2 just reads it — the cluster
  starts with YOUR users and masks instead of an empty identity plane.
- Both envs also mount the bundle's `config/*.json` + `tools/*/config.json`
  over the image's baked copies (generated `compose-*.bundle.yml`) — config
  tweaks need **no image rebuild**; edit the bundle, re-run `up`.
- `--config-bundle host` (the default) keeps the previous behavior: derive
  from the live host files.
- Debug without podman: `./startcluster bundle-node-env <bundle> <work|pg|turso|external-*>`
  prints the env the bundle would generate.

Design + edge cases: `plans/pod-config-bundle-2026-09-17.md`. Bundles hold
REAL secrets — keep them private (folder 700 / files 600; `--zip` chmods 600).

## Migration — scrape / backup / export-data (pod → bundle → new pod)

Config you change *while working in a pod* (users, masks, env) lives in the
pod's DB and generated env — not in your worktree. These commands close the
loop. **Ownership rule: only POD-OWNED state is scraped; external data planes
(host turso dir, LAN Postgres, Qdrant) are never touched.**

```bash
# 1) config plane: promote the running pod's state into its bundle
./startcluster work scrape            # users+masks from the pod DB (exec) + current work.env (stripped)
./startcluster test scrape            # same for the bench (pg topology; default bundle from node.env header)

# 2) state plane: pg_dump <-> restore (works exec-based, no published ports)
./startcluster work backup            # -> ~/supreme-mcp-tools-backups/work-pg-<ts>.sql
./startcluster test backup
./startcluster test restore <file>    # wipes pgdata, imports, restarts nodes (asks 'wipe')

# 3) pod-owned data stores
./startcluster work export-data       # artifacts volume -> tar.gz
./startcluster work import-data <tar.gz>
./startcluster test export-data       # MinIO objects -> dir (mc mirror)
./startcluster test import-data <dir>
```

**Migration recipe (old pod → new pod):** `scrape` the old pod → `backup` +
`export-data` → stop/clean it → boot the new pod from the refreshed bundle →
`restore` the dump + `import-data`. Notes: memory data planes on the work pod
are host-owned (the turso dir) — nothing to move; pg-topology data-plane
tables ride the dump; forward-only versions (never an old dump into an older
image). Each bundle manifest records what was scraped, from where, when.

## Topologies (first arg of `startcluster test`)

| Topology | State plane | db container | Use when |
|---|---|---|---|
| `pg` (default) | embedded postgres | yes (`compose-pg.yml`) | self-contained demo/cluster |
| `turso` | embedded libsql-server (sqld) | yes (`compose-turso.yml`) | same engine family as the tools' Turso stores |
| `external-pg` | your Postgres (managed/HA) | no | DB operated elsewhere |
| `external-turso` | Turso cloud / TCP sqld | no | cloud libSQL |

Each embedded backend owns its volume (`pgdata` / `sqldata`) — switching
topologies switches datasets; nothing is lost.

## Quickstart

```bash
cd deploy
cp node.env.template node.env       # fill in secrets + keep ONE state-plane block
echo "MINIO_ROOT_PASSWORD=<generate-one>" >> .env   # artifacts creds (gitignored)
cd ..
./startcluster test pg              # or: turso (external-* topologies skip MinIO)

# node centrals:
#   node 1 -> http://127.0.0.1:18200/health
#   node 2 -> http://127.0.0.1:19200/health
```

(Manual equivalent, without the script: build the image first —
`podman build -f deploy/Containerfile -t mcp-node .` — then
`podman-compose -f compose-common.yml -f compose-pg.yml up -d` from
`deploy/`; the script additionally does code pull, stale-image removal,
health waiting, and MinIO bucket bootstrap.)

Tool endpoints on the host (stateless URLs float across nodes):
`localhost:18002` / `18003` (node 1) and `19002` / `19003` (node 2) for
simplemcp / convertermcp. The prototype launches `simplemcp convertermcp
webmcp` per node — light tools with no external data-plane dependencies.
NOTE: only simplemcp/convertermcp are published; `webmcp` runs inside the
node but has no host port — add an `18004:8004` / `19004:8004` mapping to
expose it.
`memorymcp`/`ragmcp`/`databasemcp` need their backends reachable (add
qdrant/turso services to the compose file, or point the mounted `.env` at
shared instances) — see "Extending" below.

## Prove the shared plane (the H1/H2 demo)

```bash
# 1) create a user via NODE 1's central API (admin break-glass key)
curl -X POST http://localhost:18200/api/users \
  -H "Authorization: Bearer $MCP_MANAGEMENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"username":"clusteruser","password":"cluster-pass-9","role":"user","servers":["simplemcp"]}'

# 2) list users via NODE 2 — the user is already there
curl -H "Authorization: Bearer $MCP_MANAGEMENT_API_KEY" \
  http://localhost:19200/api/users

# 3) the two doors in one look — MCP lives on node ports, not the LB:
curl -s -o /dev/null -w 'node1 :18002 -> %{http_code}\n' -X POST localhost:18002/mcp-stateless
curl -s -o /dev/null -w 'LB    :18080 -> %{http_code}\n' -X POST localhost:18080/mcp-stateless
# 401 = MCP endpoint (auth required) · 404 = no MCP route behind the LB
```

Same demo at the MCP surface: fetch `clusteruser`'s key from node 1, call
`simplemcp` on **node 2** (`localhost:19002/mcp-stateless`) with it — any
node answers any request, because both verify against the same shared store.

## How state flows

| State | Where | Mechanism |
|---|---|---|
| Users / keys / grants | `mcp_users_store` (postgres) | `MCP_USERS_BACKEND=db`; reads fresh per verify |
| Function masks + inventory | `mcp_state_docs` (postgres) | `MCP_STATE_BACKEND=db`; per-boot reads + central writes |
| env/auth snapshot | `env_auth_snapshot` (postgres) | mirror + additive restore for bootstrap |
| `.env` | mounted `node.env` | identical on every node (deployment concern) |
| tool `config.json` | node-local | import-time bootstrap (H2b deferral) |
| MCP sessions | node-local | stateful `/mcp` needs sticky LB; `/mcp-stateless` floats |
| logs / metrics | node-local | aggregate via your stack (Prometheus scrapes 8300) |

## Extending

- **Data planes for the heavy tools**: add `qdrant` (image
  `qdrant/qdrant`) and a network Turso (libsql-server) or point the mounted
  `.env` at your existing instances; then set
  `TOOLS_LIST: "simplemcp convertermcp webmcp memorymcp ragmcp databasemcp"`.
- **LB**: any reverse proxy with health checks on the node centrals
  (`/health`); sticky sessions only if a client insists on stateful `/mcp`.
- **Management UI**: `--profile ui` adds a UI service talking to node 1.

## Current limits

- Runtime mask pushes (E1) fan out from the central API to every RUNNING
  node; a node started later reads the shared state doc at boot, so the
  surfaces converge without manual action.
- Inventory sync: run on one node only (union merge bounds the damage).
- Writes are last-writer-wins per document.
